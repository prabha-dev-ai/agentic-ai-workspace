**Date:** 2026-07-08
**Scope:** Full release audit and architecture re-validation for the v2.0.0 tag, covering everything built since the AAI-014C audit (`docs/architecture/FrameworkValidation.md`) — the multi-agent runtime, plugin platform, retrieval, and the nine cross-cutting production capabilities added in AAI-026 through AAI-034.

### What shipped

- **Retrieval:** hybrid (keyword + vector) retrieval, pluggable knowledge ranking strategies.
- **Observability:** structured logging (`ObservabilityService`), distributed tracing (`TraceManager`), metrics (`MetricsRegistry`: counters/gauges/histograms).
- **Operational primitives:** in-memory caching (`CacheRegistry`), secrets/redaction/input-validation (`SecurityService`), streaming responses (`StreamManager`), human-in-the-loop interactions (`InteractionManager`), a sequential/branching workflow engine (`WorkflowRuntime`), checkpoint & recovery (`CheckpointManager`).
- **Plugin platform growth:** 9 new plugin capabilities (`LogSinkProvider`, `SpanExporterProvider`, `MetricExporterProvider`, `CacheProvider`, `SecretProvider`, `StreamObserverProvider`, `InteractionObserverProvider`, `WorkflowDefinitionProvider`, `CheckpointStoreProvider` — added to an 11-capability pre-existing set), bringing the total to 20 capability kinds across two structural shapes (see ADR-0003).

### Known gaps, explicitly out of scope for v2.0.0

- No production LLM-driven demonstration of streaming/HITL/workflow through the actual chat pipeline (`llm.service.ts`, `agent-loop.ts`) — every AAI-026→034 story built its capability as standalone infrastructure without retrofitting the existing (non-streaming, non-interactive) agent execution path. Wiring them together is natural follow-up work, tracked informally, not a numbered story yet.
- No persistent (non-in-memory) backend shipped for caching or checkpointing — both are designed to be swappable via their plugin capabilities (`CacheProvider`, `CheckpointStoreProvider`), but no concrete database/Redis/object-storage implementation exists yet.
- Root-level `agents/`, `client/`, `shared/`, `tests/`, `tools/`, `scripts/`, `prompts/`, `memory/` directories are still empty scaffolding (`.gitkeep` only) — the entire implementation lives under `server/`. The Angular client mentioned in the original project README was never started.

## 2. Architecture Validation

### 2.1 Dependency graph (cross-cutting layer, added since AAI-014C)

```
core/bootstrap.ts
  │
  ├─► core/events/EventBus            (constructed first — everything else may subscribe/publish)
  │
  ├─► core/observability/*   ──observeEventBus──► EventBus
  ├─► core/tracing/*         ──observeEventBus──► EventBus
  ├─► core/metrics/*                              (no bus bridge — pull/scrape model)
  ├─► core/caching/*                              (no bus bridge)
  ├─► core/security/*        ──uses── config/env (via bootstrap only)
  ├─► core/streaming/*       ──connectEventBus──► EventBus
  ├─► core/interaction/*     ──connectEventBus──► EventBus
  │      └─► core/lifecycle/AgentLifecycle (pause/resume, when a lifecycle is attached)
  ├─► core/workflow/*        ──connectEventBus──► EventBus
  ├─► core/checkpoint/*      ──connectEventBus──► EventBus
  │
  └─► core/plugins/PluginLoader ──harvests──► every X-Provider capability above,
         wired back into the matching manager after plugin installation
```

All nine cross-cutting modules are constructed directly in `bootstrap.ts` **before** plugin installation (so they can observe install-time activity and be ready to receive plugin contributions immediately after), then registered as DI singletons. None of them import each other — each depends only on `core/events/EventBus` (optionally) and its own plugin-capability contribution types. **Circular dependencies: none**, confirmed by the same reasoning as AAI-014C (the container's cycle detector plus zero cross-imports between the nine sibling modules).

### 2.2 Layer diagram (updated)

```
L4  HTTP            app.ts, routes/, controllers/            Express lives ONLY here (tested)
L3  Composition     core/bootstrap.ts, core/tokens.ts        only place that constructs services (tested)
L2  Domain          services/, planner/, executor/,          never imports L3/L4 (tested)
                    agents/, memory/, knowledge/, tools/
L2' Cross-cutting   core/observability, core/tracing,        sibling modules, no inter-imports;
                    core/metrics, core/caching,               each optionally bridges core/events
                    core/security, core/streaming,
                    core/interaction, core/workflow,
                    core/checkpoint
L1  Infrastructure  core/container/, core/events/,            imports nothing outside itself (tested
                    core/lifecycle/, core/plugins/            for core/container specifically)
L0  Leaf data       config/env.ts, prompts/, types/           no dependencies on other layers
```

Every rule marked "(tested)" is enforced by `src/core/architecture.test.ts` — a violation fails `npm test`, not code review. That file's four fitness functions (OpenAI client singularity, `openai` value-import confinement, `process.env` confinement, container purity, Express confinement, domain-layer upward-import ban) were re-run as part of this audit and still pass against the full v2.0.0 tree.

### 2.3 Service lifetime table (delta since AAI-014C)

All 28 tokens in `core/tokens.ts` are **singletons**, lazily constructed on first resolution — no change to that policy since AAI-014C. The nine new ones:

| Token | Backing class | State |
|-------|---------------|-------|
| `observability` | `ObservabilityService` | stateful (sink registry, counters) |
| `tracing` | `TraceManager` | stateful (exporter registry, retained traces) |
| `metrics` | `MetricsRegistry` | stateful (registered instruments) |
| `caching` | `CacheRegistry` | stateful (registered caches) |
| `security` | `SecurityService` | stateful (secret sources, redactor, policy) |
| `streaming` | `StreamManager` | stateful (observer registry, retained streams) |
| `interactions` | `InteractionManager` | stateful (observer registry, retained interactions) |
| `workflows` | `WorkflowRuntime` | stateful (definitions, retained runs) |
| `checkpoints` | `CheckpointManager` | stateful (active store swap point) |

None of the nine construct their own OpenAI client or read `process.env` directly — `SecurityService`'s `ApiKeyProvider` is handed an already-loaded value from `env.llm.apiKey` at the bootstrap call site, preserving the AAI-014C rule that `config/env.ts` is the sole environment reader (re-verified: `grep -r "process.env"` across `src/core/` still returns only `config/env.ts`, per `architecture.test.ts`).

### 2.4 Audit findings

**Still verified clean (re-checked against the current tree):**
- `new OpenAI(` appears exactly once, in `core/bootstrap.ts`.
- Every other module uses `import type { ... } from 'openai'`.
- `process.env` is read only by `config/env.ts`.
- Express is confined to `app.ts`, `controllers/`, `routes/`.
- Domain modules (`services/`, `planner/`, `executor/`, `agents/`, `memory/`, `knowledge/`, `tools/`, and now the nine cross-cutting `core/` modules) never import `controllers/`, `routes/`, or `core/bootstrap`.
- `core/container/` still imports nothing outside itself.

**AAI-014C technical debt — resolution status:**

| # | AAI-014C finding | v2.0.0 status |
|---|---|---|
| 1 | Tool registry hardwired into `agent-loop.ts` | **Resolved.** `ToolProvider` plugin capability + `PluginLoader.getToolDefinitions()`/`executeTool()` make tools an injected `ToolSource`, not a module constant. |
| 2 | `env` imported directly by domain services for `env.llm.model` | **Unchanged.** Still a live gap — `llm.service.ts`, `planner.service.ts`, `executor.service.ts`, `agent.factory.ts` read `env.llm.model` at call time. Not touched by AAI-026→034 (none of them needed LLM config). Carried forward as future cleanup, not a v2.0.0 blocker. |
| 3 | Duplicated JSON fence-stripping in `llm.service`/`planner.service` | **Unchanged.** Same two call sites, still duplicated. Cosmetic, low-risk, carried forward. |
| 4 | Naming inconsistency (`core/` PascalCase vs. kebab-case elsewhere) | **Consistently followed within `core/`.** All nine new modules use PascalCase filenames matching the AAI-014A convention. The kebab-case/PascalCase split between `core/` and the rest of `src/` is unchanged and was never meant to be unified. |
| 5 | Bootstrap tests need `LLM_API_KEY` to resolve `openai-client` | **Unchanged.** Still true; not exercised by any of the nine new modules' tests (all construct their manager classes directly, bypassing `bootstrap()` except in the handful of `bootstrap.test.ts` liveness checks added per story, which don't resolve `openaiClient`). |

**New observation for v2.0.0:** the plugin capability model now has two distinct, deliberate shapes rather than one — see ADR-0003. This is documented but was never previously called out explicitly; doing so here closes a documentation gap, not a code gap.

### 2.5 Readiness assessment

**Architecture score: 9/10.** The AAI-014C tool-registry gap (the one real inversion-of-control hole) is closed. The two remaining open items (env-by-import in domain services, duplicated JSON fence-stripping) are both mechanical, low-risk, and were correctly deprioritized in favor of the nine production-capability stories — none of them blocked those stories, and none block a v2.0.0 tag.
